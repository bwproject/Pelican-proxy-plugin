# BW Proxy & AmneziaWG for Pelican

Плагин добавляет индивидуальные настройки исходящего трафика для каждого игрового сервера Pelican и узловой агент для Linux/Docker.

> **Статус: experimental / 0.2.0.** Это первая интеграционная версия. Не включайте её сразу на всех production-серверах. Сначала проверяйте на отдельном тестовом сервере и сохраняйте SSH-доступ к узлу.

## Архитектура

- **Pelican plugin**: страница в контексте конкретного сервера, миграция БД и шифрование SOCKS5-пароля через Laravel encrypted cast.
- **Node API**: агент запрашивает desired state для своего numeric node ID по HTTPS и отдельному bearer-токену.
- **BW Proxy Agent**: запускается на каждом Wings-узле от root, обнаруживает контейнер `server-<uuid>` (с fallback на UUID) и настраивает выделенные iptables-цепочки.
- **SOCKS5**: TCP перенаправляется через локальный redsocks listener к SOCKS5 с логином/паролем. Внешний UDP и прочие не-TCP протоколы блокируются для контейнеров в режиме SOCKS5, чтобы они не обходили прокси. Это не SOCKS5 UDP Associate.
- **AmneziaWG**: политика маршрутизации по mark и отдельной таблице направляет внешний трафик контейнера в уже поднятый интерфейс, с NAT и kill-switch правилом.
- Локальные RFC1918/loopback/link-local IPv4 назначения обходят туннель, чтобы сохранить доступ к локальным Docker-сетям.

Плагин **не устанавливает AmneziaWG**, не генерирует его peer-конфигурацию и не модифицирует глобальный default route хоста.

## Ограничения и риски

1. SOCKS5 режим поддерживает только TCP. Minecraft Java обычно использует TCP для игрового соединения, но UDP-сервисы, voice chat, query и другие протоколы в SOCKS5-режиме не заработают: внешний UDP блокируется.
2. Agent использует polling и Docker inspect. Это не является синхронным хуком Wings: при первом запуске контейнера, перезагрузке хоста или недоступности панели может быть короткое окно до применения правил. Не обещается zero-leak гарантия до отдельного тестирования boot ordering и Docker lifecycle.
3. В текущей версии агент не удаляет все устаревшие `ip rule`/таблицы после смены режима; повторное применение правил идемпотентно для основных цепочек, но режимы нужно тестировать на тестовом узле. Для production требуется отдельный lifecycle cleanup.
4. Фильтрация private IPv4 CIDR рассчитана на стандартные Docker-сети. Если используется нестандартная адресация, добавьте соответствующие исключения и протестируйте маршруты.
5. Токен узла даёт доступ к конфигурациям всех серверов этого узла, включая SOCKS5 credentials, поэтому агент и его токен должны считаться root-level secrets.

## Требования

- Pelican Panel с поддержкой plugin API v1 и Filament, совместимым с используемым API.
- Linux-узел с Docker, Wings, `iptables` (iptables-nft допустим), `iproute2`, Python 3.10+ и `redsocks`.
- Уже настроенный и поднятый AmneziaWG-интерфейс, например `awg0`, для режима AmneziaWG.
- Доступ агента к панели по HTTPS с валидным сертификатом.
- Уникальный случайный токен для каждого узла.

## Установка плагина в панели

1. Сделайте резервную копию БД и `.env` панели.
2. Импортируйте ZIP плагина через **Admin → Plugins → Import**, затем нажмите Install. При ручной установке поместите папку `bwproxy` в `/var/www/pelican/plugins` и выполните `php artisan p:plugin:install`.
3. Убедитесь, что миграция `bwproxy_server_settings` выполнена. Если ваша версия панели не запускает миграции плагина автоматически, проверьте журнал установки и выполните штатный процесс миграции Pelican после проверки миграции.
4. Добавьте токены в `.env` панели. Пример для узла с numeric ID `1`:

```dotenv
BWPROXY_NODE_TOKENS='{"1":"REPLACE_WITH_A_LONG_RANDOM_SECRET"}'
BWPROXY_AGENT_TIMEOUT=10
```

Сгенерируйте токен отдельно, например `openssl rand -hex 32`. Не используйте этот пример как реальный токен. Не помещайте токены или прокси-пароли в Git.

5. Перезапустите процессы панели/queue worker согласно вашей установке, чтобы переменные окружения перечитались.
6. Откройте нужный игровой сервер в клиентской панели и выберите **Прокси / VPN**. В текущей версии изменения может делать только владелец сервера.

## Установка агента на каждом узле Wings

Сначала остановите тестовый игровой сервер. Не включайте режимы на production до проверки.

```bash
sudo apt update
sudo apt install -y python3 redsocks iproute2 iptables
sudo install -d -m 0700 /etc/bwproxy /opt/bwproxy
```

Скопируйте `agent/bwproxy-agent.py` в `/opt/bwproxy/bwproxy-agent.py`, а `agent/bwproxy-agent.service` в `/etc/systemd/system/bwproxy-agent.service`.

Создайте `/etc/bwproxy/agent.json` с правами `0600`:

```json
{
  "panel_url": "https://panel.example.com",
  "node_id": 1,
  "token": "THE_SAME_LONG_RANDOM_SECRET",
  "poll_interval": 5,
  "timeout": 10
}
```

Укажите URL своей панели, numeric ID конкретного узла и токен, соответствующий этому ID в `BWPROXY_NODE_TOKENS`.

```bash
sudo chown root:root /etc/bwproxy/agent.json
sudo chmod 600 /etc/bwproxy/agent.json
sudo systemctl daemon-reload
sudo systemctl enable --now bwproxy-agent
sudo systemctl status bwproxy-agent
sudo journalctl -u bwproxy-agent -f
```

Убедитесь, что у каждого узла свой токен и свой `node_id`. Не публикуйте вывод API: он содержит расшифрованные SOCKS5 credentials, необходимые агенту.

## Проверка перед использованием

1. Сначала проверьте API: `GET /api/bwproxy/v1/nodes/<NODE_ID>/desired` с Bearer token должен вернуть только настройки данного узла. Без токена ожидается HTTP 401.
2. На тестовом сервере выберите SOCKS5. Проверьте TCP egress, затем убедитесь, что внешний UDP не уходит напрямую.
3. Переключите тестовый сервер на AmneziaWG. Проверьте внешний IPv4, DNS, UDP и доступность локальных Docker-сервисов.
4. Остановите интерфейс AmneziaWG и проверьте, что внешний трафик тестового контейнера не уходит напрямую.
5. Перезапустите тестовый контейнер, Docker и узел; проверьте правила после каждого перезапуска.
6. Верните режим `off` и проверьте, что обычная сеть восстановилась.

**Не используйте команду глобальной очистки iptables**: агент работает только с цепочками `BWPROXY_*`, но правила и policy routing нужно проверять вручную.

## Тесты и разработка

Локальные проверки агента:

```bash
python3 -m unittest discover -s agent/tests -v
python3 -m py_compile agent/bwproxy-agent.py
```

GitHub Actions запускает Python unit tests, проверку синтаксиса PHP и JSON manifests. Эти CI-проверки не заменяют интеграционные тесты на настоящем узле с Docker/Wings и AmneziaWG.

## Удаление

1. Переведите все серверы в режим `off` и убедитесь, что трафик восстановлен.
2. Остановите и отключите агент: `systemctl disable --now bwproxy-agent`.
3. Проверьте цепочки `BWPROXY_*`, policy rules и routing tables до удаления. Не очищайте чужие firewall-цепочки.
4. Удалите файл токена `/etc/bwproxy/agent.json`, затем агент и unit.
5. Только после резервного копирования и проверки зависимостей удаляйте плагин и его таблицу.

## Безопасность

SOCKS5 password шифруется Laravel encrypted cast и зависит от `APP_KEY`. Сохраняйте APP_KEY в резервной копии: при его потере зашифрованные значения не восстановить. Токены узлов хранятся в .env панели и в root-only файле агента. Используйте HTTPS, уникальные секреты, ограничьте права доступа и не включайте debug-логи с конфигурацией.
